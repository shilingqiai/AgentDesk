# Router 路由失败案例分析

> 基于评估数据集中 hard 难度用例，分析 3 个典型误判场景及其根因与修复策略。

---

## 案例 1：单关键词歧义 — "VPN"

### 输入
```
VPN
```

### 现象
用户仅输入 "VPN" 一个词。Router 无法判断用户是想：
- 查询 VPN 使用方法（应走 **fast**）
- 报告 VPN 连接故障并创建工单（应走 **action**）

### 预期行为
首次对话中应走 **clarify**（反问用户意图），多轮对话中应根据上文推断。

### 根因分析

1. **信息不足**：单关键词不包含任何动词或意图信号。人类客服面对"VPN"三个字也无法确定意图。
2. **Router prompt 未覆盖此场景**：当前 system prompt 的 clarify 条件侧重"模糊/歧义/无关"，但 "VPN" 是企业内部合法词汇，不会触发 clarify。
3. **LLM 的默认倾向**：在没有明确动词时，LLM 倾向于判 fast（认为用户在做知识查询），但这并非总是正确的。

### 修复策略

```
方案 A（prompt 增强）：在 Router prompt 中增加单关键词规则：
  "如果用户输入仅包含 1-2 个名词且没有动词，confidence 上限设为 0.5，
   确保触发 clarify 反问。"

方案 B（对话历史感知）：检查 conversation_history，
  如果上一轮是工单相关对话，当前单关键词大概率是继续操作。
```

### 实际采取
方案 A，在 system prompt 中增加："仅有名词无动词的输入 → 降低 confidence"。

## 案例 2：隐含报修意图 — "网络太慢了影响工作了"

### 输入
```
网络太慢了影响工作了
```

### 现象
用户描述了网络慢 + 工作受影响，隐含了"需要人来处理"的诉求，但没有明确说"帮我提交工单"或"报修"。

### 预期行为
应走 **action**（创建 IT 故障工单），因为：
- "影响工作" → 业务影响信号
- 描述问题 + 隐含求助 → 行动请求

### 根因分析

1. **缺少显式操作词**：用户没有说"报修""提交工单""帮我"，LLM 可能将其归类为"描述问题"（fast）。
2. **urgency 信号未被充分利用**："影响工作了"是 P1 级别的 urgency 信号，但 Router 当前的 urgency 判断较少影响 track 选择。
3. **中文表达的间接性**：中文用户常以描述问题代替直接求助，与 Router prompt 中的"action 示例"风格不匹配。

### 修复策略

```
方案 A（urgency → track 联动）：当 urgency 信号 ≥ P1 且输入描述的是
  可操作问题（网络/硬件/系统），倾向判 action。

方案 B（Router prompt 增加间接表达示例）：
  "描述问题 + 表达困扰/影响 = 隐含求助 → action"
  在 prompt 的 action 示例中增加：
  '网太卡了没法干活' '电脑一直重启影响工作了'
```

### 实际采取
方案 A + B 组合。在 prompt 中增加间接求助示例，并在路由逻辑中增加 urgency→track 联动。

## 案例 3：复合指令过度拆分 — "查会议室空余情况然后帮我定一间"

### 输入
```
查会议室空余情况然后帮我定一间
```

### 现象
用户使用了"先查...然后定..."的复合句式。Router 可能判 **complex**，进入 TaskPlanner → 多 Agent 编排 → 耗时翻倍。但实际上，"预定会议室"这个操作本身就隐含了"检查空余→如果空则定"的步骤，不需要拆成两个独立 Agent 任务。

### 预期行为
应走 **action**，由 TicketDispatch Agent 的卡片逻辑内部处理空余检查。

### 根因分析

1. **句式误导**："先...然后..." 是典型的复合指令句式，LLM 对此高度敏感。
2. **过度拆分**：task_planner 会将其拆为 Step1:"查空余"(enterprise_rag) + Step2:"预定"(ticket_dispatch)，但实际上 ticket_dispatch 的 `_build_card` 已内置冲突检测逻辑。
3. **Agent 能力边界不清晰**：Router 不知道 ticket_dispatch 的卡片构建阶段已包含查询功能。

### 修复策略

```
方案 A（Agent capability 注册时声明"内含查询"）：在 @agent_declaration 中
  增加 capabilities: ["builtin_availability_check"]，
  Router 决策时参考此信息避免过度拆分。

方案 B（prompt 增加"伪复合指令"判断）：
  "如果复合句式中后半部分是前半部分的自然执行结果，
   不视为复合指令，按最终目标判 track。"
```

### 实际采取
方案 B，在 Router prompt 中增加规则："包含'查X然后做X'的句式，按做X（最终目标）判定 track，因为操作 Agent 内部已含查询逻辑。"

---

## 总结

| 案例 | 根因类型 | 修复方向 | 影响范围 |
|------|---------|---------|---------|
| 单关键词 "VPN" | 信息不足 | Prompt 规则 + confidence 限制 | 边界输入（~5%） |
| 隐含报修 "网络太慢" | 间接表达 | Prompt 示例 + urgency 联动 | 中文用户常用（~10%） |
| 过度拆分 "查然后定" | 句式误导 | Prompt 规则 + Agent 能力声明 | 复合句式（~5%） |

**核心教训**：路由准确率的上限取决于 prompt 对真实用户表达习惯的覆盖度——用户不会按 prompt 的"示例"说话。
